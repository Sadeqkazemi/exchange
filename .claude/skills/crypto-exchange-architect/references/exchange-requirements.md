# الزامات یک صرافی آنلاین (داکیومنت تحویلی)

> این سند را در `docs/` پروژه قرار بده و برای کشور/حوزه قضایی هدف تکمیل کن. موارد حقوقی باید توسط مشاور حقوقی محلی تأیید شوند.

## ۱. الزامات حقوقی و انطباق (Compliance)
- **مجوز فعالیت** از نهاد ناظر حوزه قضایی هدف (مثلاً در ایران: الزامات بانک مرکزی و مرکز ملی فضای مجازی؛ در اتحادیه اروپا: MiCA؛ در آمریکا: ثبت MSB در FinCEN و مجوزهای ایالتی).
- **KYC (شناخت مشتری)** چندسطحی:
  - سطح ۰: ایمیل/موبایل تأییدشده — فقط مشاهده.
  - سطح ۱: کد ملی/مدرک هویتی + تطبیق شماره موبایل با مالکیت — واریز/برداشت محدود.
  - سطح ۲: احراز چهره (liveness)، مدرک آدرس، کارت بانکی به نام شخص — سقف بالاتر.
  - سطح ۳ (شرکتی/حجم بالا): مدارک شرکت، منبع وجوه (Source of Funds).
- **AML/CFT (مبارزه با پولشویی و تأمین مالی تروریسم):**
  - بررسی لیست‌های تحریم و اشخاص سیاسی (PEP) هنگام ثبت‌نام و دوره‌ای.
  - پایش تراکنش‌ها (الگوهای ساختاردهی، واریز و برداشت سریع، حجم غیرعادی).
  - تحلیل آدرس‌های رمزارزی (Chainalysis/TRM/Elliptic) برای واریز و برداشت.
  - **Travel Rule** (FATF): ارسال اطلاعات فرستنده/گیرنده برای انتقال‌های بالای آستانه بین VASPها.
  - گزارش تراکنش مشکوک (STR/SAR) به واحد اطلاعات مالی.
- **حریم خصوصی داده:** رضایت کاربر، حق دسترسی و حذف (در حد مجاز قانونی)، نگهداری سوابق مالی طبق قانون (معمولاً ۵ تا ۱۰ سال)، محل نگهداری داده (data residency).
- **قوانین و شرایط استفاده، سیاست حریم خصوصی، افشای ریسک** و قوانین کارمزد شفاف.
- **مالیات:** گزارش‌دهی و صدور صورت‌حساب طبق قوانین محلی.

## ۲. الزامات امنیتی
- پیاده‌سازی ۵ لایه امنیتی (`security-layers.md`).
- محدودیت **یک درخواست پرداخت در روز به ازای هر IP** در API Gateway، به‌علاوه سقف روزانه به ازای کاربر و حساب بانکی.
- 2FA اجباری برای برداشت؛ whitelist آدرس برداشت با دوره انتظار ۲۴ ساعته برای آدرس جدید.
- قفل برداشت ۲۴–۴۸ ساعته پس از تغییر رمز، 2FA یا ایمیل.
- نگهداری اکثریت دارایی در کیف سرد چندامضایی/MPC.
- رعایت استانداردها: **ISO/IEC 27001**، **OWASP ASVS L3**، **PCI DSS** (در صورت پردازش کارت)، **SOC 2 Type II** (برای بازار بین‌المللی)، **CCSS** (Cryptocurrency Security Standard).
- تست نفوذ سالانه توسط شخص ثالث، Bug Bounty، ممیزی قراردادهای هوشمند (در صورت وجود).
- برنامه پاسخ به حادثه (IRP)، برنامه تداوم کسب‌وکار (BCP) و بازیابی از فاجعه (DR) با RPO ≤ ۵ دقیقه و RTO ≤ ۱ ساعت.
- بیمه دارایی‌های دیجیتال (در صورت امکان) و صندوق حمایت کاربران (SAFU-like).

## ۳. الزامات مالی و حسابداری
- لجر دوطرفه، غیرقابل تغییر و قابل ممیزی (`payment-core.md`).
- **تفکیک دارایی کاربران از دارایی صرافی** (segregation of funds) — هرگز استفاده از دارایی کاربر برای عملیات شرکت.
- **Proof of Reserves** دوره‌ای و ترجیحاً ممیزی شخص ثالث.
- Reconciliation خودکار ساعتی بین لجر، روی‌زنجیره و حساب‌های بانکی.
- مدیریت کارمزد (maker/taker، برداشت)، گرد کردن مشخص و مستند.
- گزارش‌های مالی روزانه و ماهانه برای تیم مالی و ناظر.

## ۴. الزامات معاملاتی (Trading)
- موتور تطبیق price-time priority، قطعی (deterministic) و قابل بازپخش (replay) از لاگ رویداد.
- انواع سفارش: Market، Limit، Stop-Limit، (اختیاری OCO، Post-only، IOC/FOK).
- **محافظت از بازار:** Circuit breaker برای نوسان شدید، باند قیمتی، حداقل/حداکثر اندازه سفارش، جلوگیری از self-trade.
- **پایش سوءاستفاده از بازار:** wash trading، spoofing، layering، pump & dump، front-running توسط کارکنان.
- معیار لیست کردن توکن (Listing policy): بررسی حقوقی، فنی، نقدشوندگی و ریسک.
- API عمومی برای معامله‌گران (REST + WebSocket) با محدودیت نرخ و امضای HMAC.

## ۵. الزامات عملیاتی
- مانیتورینگ ۲۴/۷، On-call، هشدار برای سرویس‌ها، نودهای بلاک‌چین، صف‌ها، موجودی کیف گرم.
- مدیریت نودهای بلاک‌چین (self-hosted + provider پشتیبان)، مدیریت reorg و تعداد تأیید مورد نیاز به ازای هر شبکه:

  | شبکه | تأیید پیشنهادی واریز |
  |------|----------------------|
  | Bitcoin | 2–3 |
  | Ethereum / ERC-20 | 12–64 (یا finalized) |
  | Tron / TRC-20 | 20 |
  | BSC | 15 |

- فرایند تغییر (Change management)، CI/CD با بازبینی کد اجباری، استقرار blue/green یا canary.
- پنل ادمین جدا (دامنه/شبکه جدا، VPN، MFA، تأیید دونفره، ثبت همه اقدامات).
- پشتیبانی مشتری با تیکتینگ، احراز هویت تماس‌گیرنده، و هرگز درخواست رمز/کد 2FA.
- نگهداری (Maintenance) اعلام‌شده و صفحه وضعیت عمومی (status page).

## ۶. الزامات تجربه کاربری و شفافیت
- نمایش واضح کارمزدها، سقف‌ها، زمان تقریبی تسویه و وضعیت تراکنش (با لینک explorer).
- اعلان برای ورود، برداشت، تغییرات امنیتی.
- تاریخچه کامل تراکنش‌ها و خروجی (CSV/PDF) برای مالیات.
- دسترس‌پذیری (WCAG 2.1 AA)، پشتیبانی RTL و چندزبانه.
- آموزش امنیتی به کاربر (فیشینگ، anti-phishing code).

## ۷. الزامات فنی غیرعملکردی
| مورد | هدف |
|------|-----|
| دسترس‌پذیری | ≥ 99.9٪ |
| تأخیر API (p95) | < 200ms |
| تأخیر موتور تطبیق (p99) | < 50ms |
| ظرفیت | ≥ 10,000 سفارش در ثانیه برای هر جفت‌ارز پرطرفدار (قابل افزایش افقی) |
| نگهداری لاگ امنیتی | ≥ 1 سال آنلاین، طبق قانون آرشیو |
| Backup | روزانه کامل + WAL پیوسته، تست بازیابی ماهانه |

## ۸. سیاست محدودیت پرداخت روزانه بر اساس IP
- قاعده: هر آدرس IP (IPv4 کامل یا پیشوند /64 در IPv6) در هر روز تقویمی (پیش‌فرض `Asia/Tehran`) فقط **یک** درخواست پرداخت ثبت می‌کند.
- اجرا در API Gateway با Redis (`SET NX` + انقضا تا پایان روز) — قبل از رسیدن درخواست به payment-core.
- پاسخ تکراری: `429 Too Many Requests` با `Retry-After` و پیام قابل فهم برای کاربر.
- **محدودیت شناخته‌شده:** کاربران پشت NAT/CGNAT (اپراتورهای موبایل، شبکه‌های اداری) یک IP مشترک دارند؛ پیشنهاد: لیست سفید IP سازمانی با تأیید compliance، و تکمیل قانون با سقف به ازای کاربر/کارت بانکی. VPN و پروکسی می‌توانند این محدودیت را دور بزنند، پس این لایه کمکی است و جای کنترل‌های KYC/AML را نمی‌گیرد.
