# استاندارد امنیتی نیکسوپی (Nixopay Security Standard)

| مورد | مقدار |
|------|-------|
| نسخه | 1.0 |
| وضعیت | لازم‌الاجرا برای همه سرویس‌ها، فرانت، زیرساخت و کارکنان |
| مالک | تیم امنیت (Security Owner) |
| بازبینی | حداقل هر ۶ ماه، و پس از هر حادثه امنیتی یا تغییر معماری |

## ۰. نحوه استفاده از این سند

- هر الزام یک **شناسه** دارد (مثل `SEC-AUTH-03`). در کد، کامیت، PR و تست به این شناسه ارجاع بده؛ مثلاً `// SEC-PAY-02: one payment per IP per day`.
- کلمات کلیدی:
  - **باید (MUST):** اجباری. ادغام کد ناقض ممنوع است.
  - **نباید (MUST NOT):** ممنوع مطلق.
  - **توصیه (SHOULD):** پیش‌فرض است. عدول از آن فقط با ثبت دلیل در PR مجاز است.
- ستون «بررسی» نشان می‌دهد هر الزام چطور اثبات می‌شود:
  - `T` تست خودکار
  - `CI` بررسی در pipeline
  - `R` بازبینی کد
  - `C` پیکربندی زیرساخت
  - `A` ممیزی دوره‌ای
- **استثنا:** هر عدول از یک «باید» نیاز به ثبت در `docs/security/exceptions.md` دارد. ثبت شامل شناسه الزام، دلیل، ریسک، کنترل جبرانی، تاریخ انقضا و تأیید مالک امنیت است.
- **سند مرجع است:** اگر کد، اسکیل یا هر سند دیگری با این سند تعارض داشت، این سند معتبر است.

## ۱. دامنه و دارایی‌ها

### دامنه
- سایت عمومی و پنل کاربر (Next.js در ریشه مخزن)
- پنل ادمین
- API Gateway و همه میکروسرویس‌های NestJS
- هسته پرداخت (`payment-core`)
- دیتابیس‌ها، صف‌ها، زیرساخت و CI/CD

### دارایی‌های حساس به ترتیب اهمیت

| رده | دارایی | نمونه |
|-----|--------|-------|
| C1 — بحرانی | پول و کلیدها | موجودی کیف پول، لجر، کلید خصوصی کیف‌ها، کلید امضای JWT، اعتبار درگاه بانکی |
| C2 — محرمانه | داده شخصی و مالی | کد ملی، مدارک KYC، شماره کارت و شبا، موبایل، تاریخچه تراکنش |
| C3 — داخلی | داده عملیاتی | سفارش‌ها، تیکت‌ها، لاگ‌ها، تنظیمات سرویس |
| C4 — عمومی | داده عمومی | نرخ ارز نمایشی، صفحات سایت |

## ۲. مدل تهدید (خلاصه)

| تهدید | نمونه در نیکسوپی | کنترل‌های اصلی |
|-------|------------------|-----------------|
| تصاحب حساب | سرقت OTP، SIM swap، فیشینگ | SEC-AUTH-*، SEC-SESS-* |
| تقلب پرداخت و بازگشت وجه | بازگشت وجه به شبای دیگران، سوءاستفاده از نرخ | SEC-PAY-*، SEC-FIN-* |
| سوءاستفاده داخلی | کارمند با دسترسی مالی | SEC-ADM-*، SEC-AUD-* |
| دستکاری داده مالی | تغییر مستقیم موجودی در DB | SEC-PAY-05..08، SEC-DATA-* |
| حمله به API | IDOR، تزریق، mass assignment، replay | SEC-API-*، SEC-SVC-* |
| حمله به زنجیره تأمین | پکیج npm آلوده | SEC-SDLC-* |
| از کار انداختن سرویس | DDoS، سیل OTP | SEC-NET-*، SEC-RATE-* |

| SEC-RATE-03 | تأیید OTP: حداکثر ۵ تلاش برای هر کد. پس از آن کد باطل می‌شود و شماره ۱۵ دقیقه قفل می‌شود. | T |
| SEC-RATE-04 | لاگین ادمین: پس از ۵ تلاش ناموفق، قفل تصاعدی برای حساب و IP. | T |

## ۵. لایه ۳ — هویت، نشست و دسترسی

### احراز هویت کاربر (OTP موبایل)

| شناسه | الزام | بررسی |
|-------|-------|-------|
| SEC-AUTH-01 | کد OTP **باید** ۶ رقمی و تولیدشده با CSPRNG (`crypto.randomInt`) باشد، با اعتبار حداکثر ۲ دقیقه و یک‌بار مصرف. | T |
| SEC-AUTH-02 | OTP **باید** به‌صورت هش (HMAC-SHA256 با pepper) ذخیره شود و **نباید** در لاگ، پاسخ API یا ابزار مانیتورینگ دیده شود. | T, R |
| SEC-AUTH-03 | پاسخ «ارسال OTP» **باید** برای شماره موجود و ناموجود یکسان باشد (جلوگیری از user enumeration). | T |
| SEC-AUTH-04 | متن پیامک **باید** شامل نام دامنه و هشدار «این کد را به کسی ندهید» باشد. توصیه: فرمت WebOTP (`@domain #code`). | R |
| SEC-AUTH-05 | برای عملیات حساس **باید** احراز مجدد (step-up) انجام شود: OTP تازه یا TOTP. عملیات حساس: افزودن یا تغییر کارت و شبا، برداشت از کیف پول، درخواست بازگشت وجه به حساب بانکی، تغییر موبایل. | T |
| SEC-AUTH-06 | توصیه: 2FA اختیاری مبتنی بر TOTP یا WebAuthn برای کاربران، و اجباری برای موجودی بالاتر از سقف تعریف‌شده. | R |
| SEC-AUTH-07 | تغییر شماره موبایل **باید** تأیید هر دو شماره قدیم و جدید را بخواهد. پس از آن برداشت و بازگشت وجه به حساب بانکی ۴۸ ساعت قفل می‌شود. | T |

### نشست و توکن

| شناسه | الزام | بررسی |
|-------|-------|-------|
| SEC-SESS-01 | Access token از نوع JWT است، با الگوریتم `ES256` یا `EdDSA`، عمر حداکثر ۱۵ دقیقه، و claimهای `iss`، `aud`، `exp`، `sub`، `jti`. الگوریتم `none` و `HS*` با کلید مشترک ممنوع است. | T |
| SEC-SESS-02 | Refresh token **باید** opaque باشد، به‌صورت هش در DB ذخیره شود، در هر استفاده rotate شود، و در صورت استفاده مجدد کل خانواده توکن باطل شود (reuse detection). | T |
| SEC-SESS-03 | Refresh token **باید** فقط در کوکی `HttpOnly; Secure; SameSite=Strict; Path=/api/v1/auth` باشد. Access token فقط در حافظه فرانت نگه داشته می‌شود و **نباید** در `localStorage` یا `sessionStorage` ذخیره شود. | R, T |
| SEC-SESS-04 | کلیدهای امضای JWT **باید** در Vault/KMS باشند، از طریق JWKS منتشر شوند و حداقل هر ۹۰ روز rotate شوند. | C, A |
| SEC-SESS-05 | کاربر **باید** بتواند نشست‌ها و دستگاه‌های فعال را ببیند و باطل کند. ورود از دستگاه جدید اعلان پیامکی دارد. | T |
| SEC-SESS-06 | عمر نشست کاربر حداکثر ۳۰ روز است. نشست ادمین ۸ ساعت است و پس از ۳۰ دقیقه عدم فعالیت قفل می‌شود. | T |
| SEC-SESS-07 | خروج از حساب **باید** refresh token را در سرور باطل کند. | T |
| SEC-SESS-08 | درخواست‌های مبتنی بر کوکی **باید** محافظت CSRF داشته باشند: double-submit token یا بررسی `Origin`. | T |

### مجوزدهی (Authorization)

| شناسه | الزام | بررسی |
|-------|-------|-------|
| SEC-AUTHZ-01 | هر endpoint **باید** صراحتاً عمومی (`@Public()`) یا محافظت‌شده باشد. پیش‌فرض گارد سراسری «نیاز به احراز» است. | T, R |
| SEC-AUTHZ-02 | دسترسی به هر منبع (سفارش، تیکت، فاکتور، کارت، کیف پول) **باید** مالکیت را در سرور بررسی کند (جلوگیری از IDOR). شناسه کاربر فقط از توکن خوانده می‌شود و هرگز از body یا query گرفته نمی‌شود. | T |
| SEC-AUTHZ-03 | شناسه‌های عمومی منابع **باید** غیرقابل حدس باشند (UUIDv7 یا ULID). کدهای نمایشی مثل `CR-48xx` و `RF-10xx` فقط برای نمایش‌اند و **نباید** کلید دسترسی باشند. | R |
| SEC-AUTHZ-04 | سطح KYC **باید** در سرور اعمال شود (سطح ۰ تا ۲ و سقف‌های هر سطح). فرانت فقط نمایش می‌دهد. | T |

## ۶. پنل ادمین و کارکنان

| شناسه | الزام | بررسی |
|-------|-------|-------|
| SEC-ADM-01 | 2FA مبتنی بر TOTP یا WebAuthn برای همه کارکنان **اجباری** است. OTP پیامکی به‌تنهایی کافی نیست. | T |
| SEC-ADM-02 | مجوزها **باید** با ماتریس نقش × حوزه × عمل (view / create-edit / delete / approve-export) اعمال شوند. override فردی **باید** ثبت شود و دلیل و تأییدکننده داشته باشد. | T |
| SEC-ADM-03 | اصل حداقل دسترسی: نقش پیش‌فرض کارمند جدید هیچ دسترسی مالی ندارد. | R |
| SEC-ADM-04 | **کنترل دونفره (four-eyes):** این عملیات به تأیید فردی غیر از درخواست‌دهنده نیاز دارند: تأیید و پرداخت بازگشت وجه بالاتر از سقف، اصلاح دستی موجودی کیف پول، تغییر کارمزد یا نرخ سرویس، تغییر نقش یا مجوز کارکنان، خروجی گرفتن از داده کاربران. | T |
| SEC-ADM-05 | هیچ کارمندی **نباید** بتواند درخواستی را که خودش ثبت کرده تأیید کند، یا عملیاتی روی حساب کاربری خودش انجام دهد. | T |
| SEC-ADM-06 | ورود ادمین فقط از IPهای whitelist مجاز است (SEC-NET-06). ورود از IP یا دستگاه جدید به مالک امنیت اطلاع داده می‌شود. | T, C |
| SEC-ADM-07 | داده حساس در پنل ادمین **باید** ماسک شود، مثل شماره کارت `6037-****-****-1234` و کد ملی. نمایش کامل نیازمند مجوز جدا است و در audit ثبت می‌شود. | T |
| SEC-ADM-08 | خروجی CSV **باید** مجوز `export` داشته باشد، ثبت شود، و در برابر CSV injection محافظت شود (فرار دادن `= + - @` در ابتدای سلول). | T |
| SEC-ADM-09 | با خروج هر کارمند، دسترسی‌ها حداکثر ظرف ۱ ساعت باطل شوند. بازبینی دسترسی‌ها هر سه ماه انجام شود. | A |

## ۷. لایه ۴ — ارتباط بین سرویس‌ها

| شناسه | الزام | بررسی |
|-------|-------|-------|
| SEC-SVC-01 | همه ارتباطات داخلی **باید** mTLS باشند (service mesh یا cert-manager). گواهی‌ها کوتاه‌عمرند (≤ ۳۰ روز). | C |
| SEC-SVC-02 | سرویس‌ها **نباید** به هدرهای هویتی بدون امضا اعتماد کنند. گیت‌وی context کاربر را با HMAC امضا می‌کند (`x-gw-signature` همراه با timestamp؛ پنجره ±۳۰ ثانیه). | T |
| SEC-SVC-03 | فقط `api-gateway`، `order-service` و `wallet-service` مجاز به فراخوانی `payment-core` هستند. این قاعده با AuthorizationPolicy در mesh اعمال می‌شود. | C |
| SEC-SVC-04 | Kafka یا NATS **باید** TLS و احراز (SASL/SCRAM یا mTLS) و ACL برای هر topic داشته باشد. رویدادهای مالی امضا می‌شوند. | C |
| SEC-SVC-05 | مصرف‌کننده‌های رویداد **باید** idempotent باشند (ذخیره `event_id` پردازش‌شده). | T |
| SEC-SVC-06 | همه فراخوانی‌های داخلی **باید** timeout، retry محدود با backoff، و circuit breaker داشته باشند. | R |
| SEC-SVC-07 | هر سرویس **باید** دیتابیس و یوزر دیتابیس مخصوص خودش را داشته باشد و **نباید** به دیتابیس سرویس دیگر وصل شود. | C, R |

## ۸. لایه ۵ — پرداخت، مالی و داده

### هسته پرداخت

| شناسه | الزام | بررسی |
|-------|-------|-------|
| SEC-PAY-01 | `payment-core` **تنها** جزئی است که موجودی را تغییر می‌دهد. سرویس‌های دیگر فقط read model دارند. | R, A |
| SEC-PAY-02 | **هر IP در هر روز تقویمی فقط یک درخواست پرداخت** ثبت می‌کند. جزئیات: <ul><li>اعمال در گیت‌وی روی همه `POST /api/v1/payments/*`</li><li>کلید Redis `payment:ip:{ip}:{YYYY-MM-DD}` با `SET NX` و انقضا تا پایان روز `Asia/Tehran`</li><li>IPv6 در سطح پیشوند `/64` شمرده می‌شود</li><li>درخواستی که پیش از رسیدن به `payment-core` رد شود سهمیه را آزاد می‌کند</li><li>whitelist سازمانی فقط با تأیید compliance مجاز است</li></ul> | T |
| SEC-PAY-03 | علاوه بر SEC-PAY-02، **باید** سقف روزانه تعداد و مبلغ برای هر کاربر و هر کارت یا شبا وجود داشته باشد، وابسته به سطح KYC. | T |
| SEC-PAY-04 | هر درخواست پرداخت، برداشت، بازگشت وجه و سفارش **باید** هدر `Idempotency-Key` داشته باشد. تکرار با payload متفاوت خطای `409` می‌گیرد. | T |
| SEC-PAY-05 | لجر **باید** دوطرفه (double-entry) باشد: جمع postingهای هر تراکنش برای هر دارایی صفر است. | T |
| SEC-PAY-06 | لجر **باید** append-only باشد: `UPDATE`، `DELETE` و `TRUNCATE` با permission و trigger ممنوع است. اصلاح فقط با تراکنش معکوس انجام می‌شود. | T, C |
| SEC-PAY-07 | هر ورودی لجر **باید** هش ورودی قبلی را داشته باشد (hash chain). ورودی‌ها در بلاک‌های امضاشده با Merkle root جمع می‌شوند و `block_hash` حداقل روزانه روی یک بلاک‌چین عمومی anchor می‌شود. | T |
